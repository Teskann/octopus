Pourquoi l'export ≠ le preview

Et pourquoi opus.pro/CapCut, eux, te rendent exactement ce que tu vois. Diagnostic du diff non commité (app/render.py, app/subtitles.py) + plan de correction.

Cause racine

Tu as deux moteurs de rendu différents qui ne se parleront jamais.

Le preview est dessiné par le navigateur : DOM + CSS (<div class="caption">, @font-face, filter:blur(), transitions CSS, WebkitTextStroke).

L'export est dessiné par ffmpeg + libass : un filtergraph (crop, overlay, gblur, drawtext, filtre ass).

Chaque détail visuel est donc réimplémenté deux fois, dans deux langages, avec deux modèles de rendu. render.py réécrit à la main frame.ts, scenes.ts et Editor.effCrop en Python. À la moindre divergence — une police qui tombe en fallback, un arrondi, un flou exprimé en pixels d'écran — les deux images partent dans des directions différentes. Ce n'est pas un bug isolé : c'est l'architecture. C'est même écrit noir sur blanc dans ton CLAUDE.md : « two renderers (CSS DOM vs libass/ffmpeg) — never bit-identical ».

Comment opus.pro / CapCut / Remotion évitent ça : il n'y a qu'un seul moteur. Soit le preview est l'export (on capture image par image la même composition canvas/DOM en headless, façon Remotion), soit le preview est un flux vidéo rendu côté serveur par le moteur d'export. Le « preview » n'est jamais une imitation de l'export — c'est la même chose. Donc par construction : ce que tu vois = ce que tu télécharges.

Deux façons de corriger (à toi de choisir)

Option A — la « bonne »

Un seul moteur : le preview EST l'export

C'est l'approche opus.pro / Remotion. On arrête de dessiner les sous-titres/overlays en ffmpeg. On rend la même composition (le même code React/canvas qui fait déjà le preview) image par image, côté serveur, dans un Chromium headless (Playwright/Puppeteer), puis on assemble les frames + l'audio avec ffmpeg. libass et drawtext disparaissent.

  • Parité pixel réelle — polices, karaoké, transitions, overlays, flou : identiques, car c'est le même rendu.
  • Fini les deux implémentations de géométrie à maintenir en parallèle.
  • Coût : ajouter un pipeline de capture headless (≈ ce que fait Remotion). Encodage plus lourd que le filtergraph pur.

Recommandé si l'objectif est « je télécharge exactement le preview, en mieux ». C'est le seul moyen d'y arriver vraiment.

Option B — la « rapide »

Garder ffmpeg, mais tuer les divergences une par une

On ne vise pas la parité pixel (impossible avec deux moteurs), mais on supprime les écarts visibles. Gains rapides, dans l'ordre d'impact :

1
Polices — installer les .ttf dans fontconfig (ou embarquer la police), et arrêter fc-match. Corrige à la fois les sous-titres ET les overlays.
2
Anti-flash — un seul Dialogue par bloc avec karaoké inline \k au lieu d'un évènement par mot.
3
Transitions — ajouter le zoom (scale/zoompan) au fondu, ou l'enlever du preview pour que les deux fassent un simple cut/fondu identique.
4
Overlays texte — les passer en ASS (comme les sous-titres) au lieu de drawtext : boîte arrondie, wrap, même police.

Recommandé pour une amélioration nette cette semaine sans refonte. Restera « très proche » mais jamais bit-identique.

Quick-win #1 — les polices (le plus rentable, ~15 min)

Rendre les polices bundlées visibles par fontconfig, une fois pour toutes :

# installer les .ttf du repo dans le fontconfig utilisateur
mkdir -p ~/.local/share/fonts/transcript
cp frontend/public/fonts/*.ttf ~/.local/share/fonts/transcript/
fc-cache -f
fc-match "Anton"   # doit maintenant renvoyer Anton-Regular.ttf, plus Noto

Puis, côté ASS, ne demande plus Bold=1 pour des fichiers mono-graisse (sinon libass re-matche et peut repartir sur Noto) :

Avant — subtitles.py L153
Style: Default,{style['font']},{fs},...,1,0,0,0,...
#                    Bold=1 ── force une graisse
#                    absente du .ttf
Après
Style: Default,{style['font']},{fs},...,0,0,0,0,...
# Bold=0 : on utilise le .ttf tel quel
# (Anton/Bebas sont déjà des display faces)

Quick-win #2 — le flash du karaoké

Avant — 1 évènement par mot (subtitles.py L205)
for gi, word in enumerate(flat):
    start = word["start"]
    end = flat[gi+1]["start"] ...
    main = _render_block(lines, gi, ...)
    events.append(_dialogue(start, end, ...))
# N mots => N Dialogue => libass re-dessine
# tout le bloc N fois => clignotement
Après — 1 évènement, karaoké inline \k
# un seul Dialogue pour tout le bloc :
# chaque mot porte {\kf<centisec>} ; libass
# colore mot par mot SANS re-créer l'évènement
main = ""
for w in flat:
    cs = round((w["end"]-w["start"])*100)
    main += f"{{\\kf{cs}}}" + _esc(w["text"])+" "
events.append(_dialogue(block_start, block_end, main))

Avec la couleur primaire = PrimaryColour et la couleur highlight = SecondaryColour, \kf fait exactement le « remplissage » karaoké TikTok — un seul évènement stable, plus de flash.

Ma recommandation

Vu ta phrase « je veux télécharger exactement ce que je vois, en mieux » — le seul chemin qui y répond vraiment est l'Option A (un seul moteur, capture headless de la composition React). C'est un vrai chantier mais c'est la raison pour laquelle opus.pro n'a pas ton problème.

Mais commence par les quick-wins #1 et #2 de l'Option B (polices + anti-flash) : c'est ~1 h de travail, ça corrige les deux défauts que tu ressens le plus fort (mauvaise police + clignotement), et ça te laisse décider si l'écart résiduel justifie le passage à l'Option A.
