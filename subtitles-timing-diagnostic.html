Diagnostic · sous-titres mot-à-mot

Pourquoi la synchro par mot est « aléatoire »

Les blocs sont bien calés, mais chaque mot ne s'allume pas au bon moment. Voici la cause exacte — et non, ce n'est pas une limite de Whisper.

⚡ Verdict en une phrase

Whisper calcule déjà des horodatages par mot très précis (via le DTW, qui est bien activé chez nous), mais il les écrit dans un champ à part appelé t_dtw. Or notre code app/whisper.py lit le mauvais champ (offsets, les temps grossiers), et ignore complètement t_dtw. On jette donc la précision qu'on a payée, puis on « étale » les temps grossiers dans le bloc → l'impression d'aléatoire.

1. Le symptôme, précisément

Ton observation est juste et c'est un indice fort :

Début de chaque bloc ✓ juste → Position des mots ✗ dans le désordre

Ce contraste précis — bornes correctes, intérieur faux — est la signature d'un problème bien identifié, pas d'un bruit aléatoire. Cela veut dire que les temps de segment (le [start, end] de chaque ligne de sous-titre) sont fiables, mais que les temps de chaque mot à l'intérieur ne le sont pas. Reste à savoir pourquoi.

2. Ce que Whisper nous donne réellement

Pour chaque token, whisper-cli -oj -ojf écrit dans le JSON deux horodatages de nature différente :

Champ JSONOriginePrécision mot
offsets.from / .to Temps « décodeur » (token.t0 / t1) — heuristique tirée des tokens d'horodatage. Grossier, calé sur des fenêtres. Médiocre
t_dtw Alignement Dynamic Time Warping sur les têtes d'attention du modèle. C'est l'horodatage précis par mot. Excellente

Voici le code source de whisper.cpp qui écrit le JSON par token — on voit clairement les deux champs cohabiter :

whisper.cpp — examples/cli/cli.cpp (sortie JSON par token)value_s("text", mt.text.c_str(), false);
if (mt.data.t0 > -1 && mt.t1 > -1) {
    // "offsets" = t0/t1 grossiers (temps décodeur)
    times_o(mt.data.t0, mt.t1, false);   // → offsets.from = t0*10 (ms)
}
value_i("id",  mt.data.id, false);
value_f("p",   mt.data.p,  false);
value_f("t_dtw", mt.data.t_dtw, true);  // ← LE bon horodatage, en centisecondes (-1 si absent)

✓ Bonne nouvelle : le DTW est bien activé chez nous

J'ai vérifié : app/config.py passe WHISPER_DTW = "large.v3.turbo", et c'est exactement l'un des presets valides attendus par whisper.cpp (if (params.dtw == "large.v3.turbo")), qui correspond bien au modèle ggml-large-v3-turbo.bin. Donc whisper calcule bel et bien le champ t_dtw précis à chaque exécution. Le problème n'est pas là — il est côté lecture.

3. Le bug : on lit le mauvais champ

Dans app/whisper.py, la fonction qui transforme les tokens en mots lit offsets (les temps grossiers) et ne regarde jamais t_dtw :

app/whisper.py — _tokens_to_words()  (lignes ~100-102)off = tok.get("offsets", {})
t0 = off.get("from", 0) / 1000.0   # ← temps GROSSIER (décodeur)
t1 = off.get("to", off.get("from", 0)) / 1000.0
# t_dtw n'est lu NULLE PART dans tout le fichier.

Ensuite, _fit_words_to_segment() prend ces temps grossiers et les redistribue proportionnellement à l'intérieur du segment (transformation affine), en forçant le premier mot sur seg_start et le dernier sur seg_end :

app/whisper.py — _fit_words_to_segment()  (le « rattrapage »)span  = raw_end - raw_start
scale = seg_span / span
for w in words:
    w.start = seg_start + (w.start - raw_start) * scale   # étale les temps grossiers
...
w.end = words[i + 1].start   # fin d'un mot = début du suivant (pas de trou)

C'est là que ton symptôme naît, mécaniquement :

  • Le 1er et le dernier mot sont épinglés aux bornes du segment → le bloc a l'air calé
  • Les mots du milieu sont placés selon des proportions issues de données peu fiables → position perçue comme aléatoire

Cette fonction est un pansement écrit pour compenser des temps grossiers. Mais on n'en a pas besoin : les vrais temps existent déjà dans t_dtw. On rafistole une donnée qu'on aurait juste dû lire correctement.

4. Pourquoi les autres éditeurs y arrivent

Opus.pro, Submagic, Veed & co ne font pas de magie — ils utilisent une des deux approches, et nous sommes à un tout petit pas de la première :

ApprocheCe que c'estNous
Lire le DTW de Whisper Utiliser directement les horodatages alignés (t_dtw / ce que fait whisper-timestamped). On les calcule mais on ne les lit pas
Alignement forcé dédié WhisperX : un 2e modèle (wav2vec2, CTC) réaligne phonétiquement le texte sur l'audio. Précision maximale. Pas encore fait

Donc : ce n'est pas une limite de Whisper. C'est un champ non lu chez nous.

5. Le correctif

Correctif principal — lire t_dtw en priorité

Une modification chirurgicale dans _tokens_to_words() : préférer t_dtw quand il est disponible (≥ 0), sinon retomber sur offsets. Attention aux unités : t_dtw est en centisecondes (÷ 100 → secondes), alors que offsets est en millisecondes (÷ 1000).

✗ Actuel — lit les temps grossiers
off = tok.get("offsets", {})
t0 = off.get("from", 0) / 1000.0
t1 = off.get("to",
   off.get("from", 0)) / 1000.0
✓ Corrigé — DTW prioritaire, repli sur offsets
dtw = tok.get("t_dtw", -1)
off = tok.get("offsets", {})
if dtw is not None and dtw >= 0:
    t0 = dtw / 100.0  # centisec → s
    t1 = t0        # fin recalculée
else:
    t0 = off.get("from", 0) / 1000.0
    t1 = off.get("to",
       off.get("from", 0)) / 1000.0

Note : t_dtw donne un point par token (le début du mot), pas une paire début/fin. C'est parfait ici — _fit_words_to_segment() recalcule déjà la fin de chaque mot comme « début du mot suivant ». On peut donc alléger cette fonction pour qu'elle respecte les temps DTW (simple clamp aux bornes + non-décroissance) au lieu de les ré-étaler par transformation affine.

⚠ À vérifier une fois le correctif en place

  • Que t_dtw n'est pas -1 dans le JSON produit (regarde data/projects/<id>/… ou un run de debug). S'il est toujours à -1, c'est que le build de whisper.cpp n'a pas les têtes d'alignement → il faudra reconstruire avec le support DTW.
  • Que le rendu (export) reste identique : les captions viennent du même CaptionBlock partagé, donc corriger les temps corrige à la fois l'aperçu et l'export, gratuitement.

Option supérieure (plus tard) — alignement forcé

Si après le correctif t_dtw tu veux la précision « pro » absolue (mots serrés type TikTok, robustes aux hésitations et à la musique), l'étape suivante est l'alignement forcé à la WhisperX : un passage wav2vec2 (CTC) 100 % local qui recale chaque mot sur l'audio. Plus lourd (un 2e modèle, du VRAM), mais c'est le vrai plafond de qualité. À réserver si le DTW ne suffit pas.
