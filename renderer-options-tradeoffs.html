Renderer « façon Remotion »

Deux façons de construire l'export. Les deux capturent Chrome en train de rendre ton CSS — donc les sous-titres, le flou, les polices TikTok, le contour de texte et la boîte arrondie sont identiques au preview dans les deux cas. La vraie différence : qui gère les parties difficiles (frames vidéo exactes, audio, la boucle de rendu) — toi, ou le framework.

🅐  Utiliser Remotion framework

Une composition Remotion re-rend le clip de façon déterministe à partir de project.json, en partageant les modules purs (captions.ts, frame.ts, scenes.ts, styles). Le backend appelle @remotion/renderer.

Frames vidéo exactes — <OffthreadVideo> extrait la bonne image via ffmpeg, pas de seek d'un <video> vivant. C'est le problème dur, résolu.
Audio automatique — <Video>/<Audio> sont collectés, mixés et muxés pour toi (volume, trim, sync).
Rapide — rendu des frames en parallèle (plusieurs onglets/process Chrome), compositor Rust.
Progress, reprise, gestion d'erreurs, delayRender() pour attendre les assets — déjà là.
Battle-tested : c'est exactement l'outil que tu as pointé.
Composition parallèle à maintenir — le layout de compositing est ré-exprimé en Remotion (useCurrentFrame, <Sequence>, interpolate). On partage les sous-composants, mais ce n'est pas littéralement le preview.
Toolchain lourde — bundler Remotion propre (séparé de ton Vite), un process node que le backend Python lance.
Licence non permissive — gratuit en perso/petite équipe, mais Company License payante au-delà. À vérifier si ça devient un produit.
Encodage surtout CPU (x264). Peu de contrôle pour brancher VAAPI GPU sur ta gfx1030.
🅑  Capture headless maison Playwright + ffmpeg

Un petit pipeline backend charge tes composants preview existants (mode déterministe piloté par un prop t) dans Chromium headless, avance frame par frame, screenshote, puis muxe l'audio source du clip via ffmpeg.

Parité maximale — on charge le même bundle, les mêmes composants, le même CSS. Zéro « deuxième rendu » à faire dériver.
Dépendances minimales & permissives — Playwright (Apache-2.0), ton ffmpeg. Rien de propriétaire.
Contrôle total de ffmpeg — VAAPI GPU sur gfx1030, CRF, faststart : tu choisis tout.
Colle à l'esprit du repo : local, simple, peu de concepts nouveaux.
Tu possèdes le problème dur — la précision des frames vidéo. Seeker un <video> par frame dans Chrome est lent et pas toujours frame-exact (surtout avec plusieurs scènes simultanées).
Boucle de rendu à écrire — stepping, screenshot, pipe PNG→ffmpeg, extraction/trim audio, progress. ~300–500 lignes à nous.
Rendu séquentiel par défaut (1 onglet). Paralléliser = travail en plus.
Les composants preview sont mêlés à la logique de lecture live (SceneStage nudge le playbackRate) — il faut ajouter un « mode rendu » déterministe proprement.

// remotion/Clip.tsx — composition déterministe
export const Clip = ({project, clip}) => {
  const f = useCurrentFrame();      // frame courante
  const t = clip.start + f / fps;
  return (
    <AbsoluteFill>
      <OffthreadVideo src={sceneSrc} /* frame exacte */ />
      <Captions cue={cueAt(t)} style={style} />
      <Overlays t={t} />
    </AbsoluteFill>
  );
};
// backend: renderMedia({composition, props, codec})

Spécifique à ton projet

Le point qui tranche vraiment : tes clips ont des changements de scène (plusieurs vidéos) + reframe. Rendre ça frame-exact, c'est là que le seek d'un <video> par frame de l'option B est le plus fragile et le plus lent — et exactement ce que OffthreadVideo de l'option A résout sans effort. À l'inverse, ton envie de GPU AMD (VAAPI gfx1030) et de rester léger/permissif/local penche vers l'option B.

Ma lecture

Si le but est « ça marche, robuste, je ne veux pas déboguer la vidéo » → Option A (Remotion). Elle résout précisément les deux parties dures (frames vidéo exactes + audio) que tu devrais sinon écrire et fiabiliser toi-même, et c'est l'outil que tu as déjà repéré.

Si tu valorises le repo minimal, la réutilisation exacte du preview, la licence permissive et l'encode GPU → Option B (maison). Parité maximale par construction, mais tu prends le risque « seek vidéo par frame ».

Mon léger penchant : Option A pour ce cas précis, à cause du multi-scènes frame-exact — sauf si la licence non-permissive ou l'obligation d'encoder sur GPU AMD sont des contraintes fortes pour toi, auquel cas B. Dis-moi ce qui compte le plus (robustesse vidéo, légèreté/licence, ou GPU) et je pars dessus.

Note pratique commune : je ne peux pas lancer node/npm ni Playwright dans le sandbox — dans les deux cas tu feras l'install et les runs toi-même ; j'écris le code avec soin et tu valides par un run.
